# UnboundOS — Project Constitution for Claude Code

UnboundOS is a single-address-space, bare-metal x86_64 dataflow operating environment.
The primary execution unit is a **verified executable graph**, not a process or thread.
Authoritative spec: `docs/UnboundOS_Tech_Spec_v2_1_1_Fidelity_Hardening.pdf`
(referenced as "spec" below).

This file is the binding contract for all agent work in this repo. When the
spec and this file conflict, the spec wins; flag the conflict.

---

## 1. Identity (spec §1.1)

- Single address space. Trusted Ring 0 modules. No POSIX, no Unix, no sandbox.
- Persistent artifacts (`.MOD`/`.UMDL`) are **symbolic and verified**.
- Runtime graphs use raw pointers, but raw pointers never appear in persistent files.
- The system is unsafe by design but **not** undefined by design.

## 2. Hard Rules — non-negotiable

These map to spec §1.4–§1.10 and §14.1. Violating any of them is a bug, not a tradeoff.

| # | Rule | Spec |
|---|------|------|
| H1 | Persistent files MUST NOT contain raw pointers, live function addresses, kernel virtual addresses, host paths, or dynamic library refs. | §1.4 |
| H2 | The **only** legal path to a `GraphRuntime` is `graph_load_from_umod` → verifier → `graph_compile_verified`. No dev-mode bypass, no test shortcut, no editor direct constructor. | §1.9, §5.7 |
| H3 | No hidden execution. All meaningful work is graph nodes, boot init, ISRs, or panic paths. The LLM subsystem is subject to this rule. | §1.8, §10.3 |
| H4 | LLM output MUST NOT mutate state directly. Tool-planning lands in `structured_action_buffer` → schema validator → graph verifier → operator approval → reload. | §1.7, §10.18 |
| H5 | No eval node, no LLM-to-module shortcut. Generated code is text until an operator manually loads it as a module. Any future dynamic loading capability is named `requires_dynamic_module_load` and disabled by default. | §1.10 |
| H6 | No SIMD path is reachable except through the loader-selected dispatch table chosen from CPUID + XCR0. AVX is never assumed. | §2.3, §3.3, §11.2 |
| H7 | Every allocation belongs to a named arena and a declared lifetime phase. Arena exhaustion is deterministic and reports arena identity. | §4.4–§4.11 |
| H8 | Graph-visible storage references are opaque resource IDs (`model:…`, `index:…`, `blob:…`, `graph:…`, `font:…`, `profile:…`). FAT32 paths and `local://` URLs MUST NOT cross the storage adapter boundary. | §6.8, §7.2 |
| H9 | Boot is never blind. Every boot path produces serial heartbeat (or equivalent boot-diagnostic-buffer fallback) before graphical init. | §1.6, §3.9 |
| H10 | Fatal exceptions go through SSOD with the structured diagnostic record. Silent failure, reboot loops, swallowed verifier errors are invalid outcomes. | §1.5, §9 |

If a change *appears* to require violating one of these rules, that is a signal the design
needs adjustment, not the rule. Stop and ask the operator.

## 3. Convenience Creep — forbidden patterns

The most likely failure mode of this project is convenience creep: a local shortcut that
silently reintroduces a rejected architecture (spec §0.4). These specific shapes are
forbidden:

- Treating FAT32 paths or `local://` strings as graph-level resource identifiers.
- Adding a hidden inference loop, worker thread, or queue not represented as a graph node.
- Building a `GraphRuntime` directly inside the IDE editor or a unit test.
- A developer-mode flag that skips graph verification.
- Calling `matvec_q4_avx2` or any backend-specific tensor symbol without going through
  the loader-selected dispatch table.
- An LLM tool-planning output that becomes a graph mutation without operator approval.
- Treating scratch arena exhaustion as a generic panic without arena identity.
- Code generated by the assistant flowing from text directly into execution.
- `#[derive(Serialize, Deserialize)]` on any runtime struct containing pointers or
  function addresses. UMOD/UMDL serialization uses fixed-width integer layouts only.

If you see one of these in a diff or a proposal, refuse to extend it. Suggest the
canonical path. Cite the spec section.

## 5. Build, Test, Run

The standard workflow. Codex can run the non-mutating checks directly; commands
that require unavailable local tooling must be reported as blockers.

```bash
# Build the kernel for the custom target
cargo build -p kernel --target x86_64-unboundos.json -Z build-std=core,alloc -Z build-std-features=compiler-builtins-mem -Z json-target-spec

# Run smoke tests in QEMU (captures serial)
make qemu-headless

# Lint the kernel for std leakage
cargo clippy --workspace --all-targets -- -D warnings

# Address-scan all persistent fixtures
python3 scripts/address_scan.py tests/golden_graphs tests/golden_models

# Aggregate fidelity gate sweep (the canonical pre-commit check)
make fidelity
```

If `make` targets are missing, propose a `Makefile` patch rather than improvising
shell pipelines per session.

## 6. Conventions

- **`#![no_std]`** is mandatory in `kernel/`. CI will fail if `std` leaks in.
- **`#[repr(C)]`** on every struct that crosses an artifact boundary or an FFI boundary.
- **Fixed-width types** (`u8`, `u16`, `u32`, `u64`) for every persistent field. No `usize`
  in artifact descriptors.
- **No `derive(Serialize, Deserialize)`** on structs containing pointers or `ModuleFn`.
- **Little-endian** for all multi-byte binary formats unless explicitly noted (spec).
- **Resource references**: `resource_type ":" opaque_id` only. The grammar is in spec §6.8.
- **Error types** live in `kernel/src/error.rs` and always carry context (arena ID, graph
  ID, node ID, model ID where applicable).
- **Arenas** allocate only through guard functions like `with_graph_arena(graph_id, |a|
  ...)`. Direct allocator calls outside guards are a review-blocker.
- **Diagnostics** for any fatal path use the `DiagnosticContext` struct and route through
  `kernel_panic(reason, ctx)`.

## 9. The 8 review questions (spec §14.3)

Every change touching storage, graph loading, LLM inference, arenas, SIMD, or IDE
mutation must answer:

1. Does this introduce a path around symbolic artifact verification?
2. Does this expose POSIX-like paths above the storage adapter?
3. Does this execute work outside the orchestrator without a graph-visible representation?
4. Does this let the LLM mutate state instead of proposing a change?
5. Does this allocate from an arena outside the declared lifetime phase?
6. Does this assume AVX/AVX2/AVX-512 instead of checking capabilities?
7. Does this make boot, crash, or load failure less diagnosable?
8. Does this weaken deterministic replay guarantees?

If any answer is yes or unclear, run `python3 scripts/verify.py --mission
current` and `make fidelity` when available, then stop until the operator
confirms.

## 10. Definitional anchors

- **Arena** — bounded memory region with explicit lifetime and failure behavior.
- **Graph** — executable dataflow structure of nodes and wires.
- **Epoch** — monotonic version counter for wire readiness.
- **Capability** — symbolic requirement declared by graph, node, model, or backend.
- **Operator** — the human controlling the system. Final authority on graph mutation,
  storage overwrite, model loading, boot config, and generated-code execution.
- **SSOD** — Snark Screen of Death. Fatal structured diagnostic path.
- **Macro-node** — verified node internally representing a larger graph fragment or
  batched op. Its inputs, outputs, memory, and nondeterminism are declared.

## 11. Working style

- Proportional rigor. The spec is publication-grade; match it.
- Zero placeholders in deliverables. If a feature is genuinely deferred, mark it
  `unimplemented!()` with a TODO citing the milestone (M0–M12, spec §13).
- Cite spec sections in code comments where rules are encoded, e.g.
  `// spec §5.7: single verifier gate`.
- When proposing a refactor, name the convenience-creep pattern it avoids.
- Prefer single-file deliverables for tools and fixtures where practical.
- Dark-themed, typographically precise outputs for any HTML or doc artifact.

## 12. Out-of-scope until explicitly unlocked

- POSIX/Linux/Windows binary compatibility
- General driver support
- Multi-user security
- Package management
- Web browser
- Real-time hard guarantees
- LLM training or fine-tuning
- GPU acceleration as a primary backend (CPU first, spec §11.1)
- Full filesystem compatibility (FAT32 is staged behind raw sectors and append-only
  store, spec §7.1)

If a request would step outside this list, name the line being crossed and ask.

## 13. Mission / Campaign workflow

UnboundOS code changes happen inside **milestone campaigns**. The structure is
three files plus an archive directory:

- `MILESTONE_CATALOG.md` — registry of M0–M12 (spec §13). Exactly one row is
  `IN-PROGRESS` at a time. Each row names its owning campaign file.
- `CURRENT_CAMPAIGN.md` — working copy of the active milestone's campaign file.
  Defines `## Macro sequence` (numbered Steps) plus per-Step `Purpose:`,
  `Allowed files:`, `Required work:`, `Validation:` blocks. May contain an
  explicit `# Step N — Review gate` step that forces a mandatory stop.
- `CURRENT_MISSION.md` — operator-facing entrypoint. Names the active
  milestone, the campaign branch, required reads, baseline to verify, and the
  final-report format. This is the file `/go` reads first.
- `docs/campaigns/` — archive. Each milestone has one file here; the top-level
  `CURRENT_CAMPAIGN.md` is a working copy of the active one. Completed campaign
  files are never edited.

Rules:

- One campaign branch per milestone (`campaign/m<N>-<slug>`).
- One commit per Step. Push every Step. Never push to `main` during campaign
  execution. Never `git push --force`.
- A Step's `Allowed files:` block is binding. Edits outside the listed paths
  require a new step (or a new campaign), not silent scope expansion.
- A Step's `Validation:` block doubles as the detection oracle the
  `current-mission` agent uses to decide whether the Step is already done.
- `Review gate` Steps are mandatory stops. The operator must explicitly clear
  them before subsequent Steps run.
- Catalog rows flip `IN-PROGRESS → DONE` only when their gate criteria are
  reproducible from a clean checkout via `make gates`.

The `/go`, `/repo-state`, and `/fidelity-lint` commands under
`.claude/commands/` drive this workflow. The `current-mission`,
`campaign-state`, `spec-refresher`, and `milestone-explorer` agents under
`.claude/agents/` are the executors and diagnostics.

## 14. The /go contract

When the operator types `/go` (or "go", or "run the current mission"), Claude
delegates to the `current-mission` agent and runs the following sequence:

1. Read `CURRENT_MISSION.md`. Parse `## Required reads`.
2. **Single parallel preflight burst** in one message:
   - `Read` every required-reads path.
   - `Bash`: `git status`, `git log --oneline -10`,
     `git log --merges --oneline origin/main | head -10`,
     `git branch --show-current`, `make repo-state`, `make gates`.
   - `Task`: `subagent_type=campaign-state`,
     `subagent_type=fidelity-gate-reviewer` (scoped to the diff).
3. Synthesize. Stop immediately on any blocker (see stop list below).
4. Pick the lowest-numbered Step whose `Required work` is not yet observable.
5. Refuse any Edit/Write outside the Step's `Allowed files:` set.
6. Execute the Step.
7. Run the Step's `Validation:` block verbatim. Stop on first failure.
8. Generate the commit message via
   `python3 scripts/milestone_advance.py <M-id> <step-n>`. Stage only the
   `Allowed files`. Commit.
9. `git push -u origin <campaign-branch>`. Never main. Never `--force`.
10. Loop back to step 4. **Do as much work as the gates allow in one
    invocation.**
11. Emit the final report from `CURRENT_MISSION.md ## Final report format`.

`/go` stops at the first of:

- **Review gate** — the next Step's header is `# Step N — Review gate`.
- **Gate failure** — any of `make gates` sub-gates fail (fmt, clippy, test,
  address-scan, fidelity matrix, qemu-smoke).
- **Hard-rule violation** — `fidelity-gate-reviewer` returns BLOCK or any
  pre-tool hook (e.g., `hook_pre_graph_runtime.py`) refuses an edit.
- **Branch guard** — current branch is `main` or any non-campaign branch.
- **Stale baseline** — `## Baseline to verify` in the mission disagrees with
  `make repo-state`.
- **Out-of-scope edit needed** — required path is not in the Step's
  `Allowed files`.
- **Ambiguity** — `campaign-state` returns `USER-JUDGMENT`.
- **Done** — macro sequence exhausted; operator may open the final PR.

`/go` MUST NOT bypass any of H1–H10. If a Step's `Required work` appears to
require a violation, the agent escalates to the operator instead of executing
the Step.
